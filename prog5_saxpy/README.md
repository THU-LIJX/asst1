# Problem 5：SAXPY 为什么没有明显的 ISPC 加速

你的判断方向正确：本题主要考察低计算强度下的访存带宽限制。还需要补上一个本机的关键事实：名为 `saxpySerial` 的 C++ 基线已经被 Clang 自动向量化。因此，这次比较不是“纯标量对 SIMD”，而是两个 SIMD 实现，以及多任务 SIMD。

本目录回答必做第 1 题和第 2 题的写分配问题；第 3 题实际尝试了参数调优，但没有得到足以宣称显著优化的结果。保留你的 `main.cpp` 输出修改，未修改 SAXPY 内核、原 Makefile 或课程 README，也没有采用任何 QoS 或绑核设置。

## 1. 运行结果与原因

### 实测：没有稳定的大幅加速

平台为 Apple M3、4 个性能核心和 4 个能效核心、16 GiB 内存。使用当前工作区源代码，N=20,000,000，C++ `-O2`，ISPC `-O3 --target=neon-i32x8 --arch=aarch64 --pic`。每个进程内部三个实现各计时 3 次、分别取最短值；下表为 10 个独立进程的中位数及第 25–75 百分位。初始化与逐元素结果校验不计时。

| 实现 | 耗时中位数 ms | 耗时 IQR ms |
| --- | ---: | ---: |
| C++ 基线 | 3.477 | 3.102–4.373 |
| ISPC，无 tasks | 3.306 | 3.059–3.778 |
| ISPC，64 tasks | 3.149 | 2.931–3.817 |

比值先按每次启动计算，再取中位数，因此不一定等于上表两个中位耗时的比值。

| 测量阶段 | C++ / ISPC | C++ / task ISPC | ISPC / task ISPC |
| --- | ---: | ---: | ---: |
| 配置扫描中的默认配置，10 次 | 1.054× | 1.079× | 1.028× |
| 单独确认默认程序，20 次 | 1.161× | 1.145× | 1.001× |

第 1 题可以报告：本轮 task ISPC 相对原 C++ 基线约 **1.08×**，相对单核 ISPC 仅约 **1.03×**。它没有接近按核心数线性增长的加速。

在单独确认的 20 次运行中，有 **6 次**单核 ISPC 比 C++ 慢。该阶段 SIMD 加速比 IQR 为 0.888–1.324×，跨过 1。这重现了你看到的现象，但也说明它不是每次都发生。当前运行环境波动较大，不能仅凭一次运行或者几个百分点的差异，断定某个编译器始终更慢。全部记录均保留，没有删除较慢运行；也没有通过更改优先级来稳定结果。

### 原因一：C++ 基线已经使用 SIMD

采用原 Makefile 相同参数编译 `saxpySerial.cpp`，Clang 明确报告：

```text
vectorized loop (vectorization width: 4, interleaved count: 4)
```

生成的 C++ 主循环包含四条 `fmla.4s`，每轮处理 16 个 float；ISPC 主循环包含两条 `fmla.4s`，每轮处理 8 个 float。两者都使用 NEON FMA，一次 FMA 按一次乘法加一次加法计为 2 FLOP。代码生成证据保存在 [codegen/](results/codegen/)，其中 [编译诊断](results/codegen/default_vectorization.log)明确记录了自动向量化。Clang 的循环向量化与交错展开机制见 [LLVM 官方说明](https://llvm.org/docs/Vectorizers.html)。

作为对照，只在临时副本的 C++ 编译参数中加入 `-fno-vectorize -fno-slp-vectorize`，C++ 耗时中位数为 6.125 ms，ISPC 为 3.596 ms，逐次比值的中位加速比为 1.820×。其 C++ 汇编变为逐个元素的 `ldr s`、`fmadd`、`str s`。这支持自动向量化已改善原基线的解释；不能把禁用优化后变慢的基线用于宣称优化了原程序。

ISPC 的 `neon-i32x8` 指 8 个逻辑 lane，M3 原生 NEON 是 128 位、每个向量 4 个 float。逻辑宽度较大，不等于代码一定比 C++ 编译器生成的向量循环更快。上述展开差异可能影响循环控制和访存调度，但未用硬件计数器量化它对时间差的贡献。

### 原因二：计算少，搬运数据多

每个元素计算 `result[i] = scale * X[i] + Y[i]`：

| 内容 | 每元素工作量 |
| --- | ---: |
| 乘法、加法 | 2 FLOP |
| 读取 X、Y | 8 字节 |
| 写 result | 4 字节 |
| 按两读一写计算的逻辑数据量 | 12 字节 |
| 另计输出写分配读入时的数据量 | 16 字节 |

计算强度约为 `2/12 = 1/6 FLOP/字节`；按题目写分配模型则为 `2/16 = 1/8 FLOP/字节`。这是数据搬运多、每份数据上计算少的内核。Roofline 模型将性能近似约束为 `min(计算吞吐上限, 可持续带宽 × 计算强度)`；带宽受限时，增加算术并行能力不会同比提高性能。见 [NERSC Roofline 说明](https://docs.nersc.gov/tools/performance/roofline/)。

N=2000 万时，两读一写合计 240 MB 的逻辑数据。任务划分不会减少这些数据量；多个核心共同使用内存系统，其总带宽不会随着核心数倍增。如果单线程已经获得较高的数据吞吐，多核只能填补剩余空间，还需要支付提交、调度和同步开销。本仓库的 macOS 任务运行时使用 GCD，复用系统工作线程，不是每个 task 都新建一条系统线程。

与 Mandelbrot、迭代 sqrt 不同，这里的每个元素执行同样的算式，没有耗时不等的迭代循环。N 可被 8 整除，单核 ISPC 的完整主循环也不需要逐元素处理尾部掩码。不能用“各 lane 迭代次数不同”来解释这道题。

### 能否改写成接近线性加速？

**在同一台机器上，保持这些大数组和相同的两读一写语义，带宽饱和后不能通过增加 CPU 核心或向量宽度获得近线性加速。**这不等于完全没有优化空间：更好的访存调度、减少额外流量、合适的任务粒度可能有收益。但不能直接套用前几题的 4×、8×或 SIMD×核心数的预期。

Apple 给 M3 标注的内存带宽为 100 GB/s，参见 [官方技术规格](https://support.apple.com/zh-cn/118551)。如果假设冷数据全部经过 DRAM、只有两读一写且没有额外流量，240 MB / 100 GB/s ≈ 2.4 ms，可作为理想模型的数量级参考，不能当作已测到的持续带宽或含缓存执行的硬下界。这两阶段默认配置中最快的 C++ 记录为 2.767 ms，逻辑有效数据速率约 86.7 GB/s。这与访存占重要地位的解释相符；较慢记录还会混入调度、频率及背景负载的影响。

这里的 memory-limited 主要指带宽约束，不是 16 GiB 内存装不下数组。本轮未采集内存控制器计数、cache miss 或线程调度轨迹，不能精确分离 DRAM、缓存、核心内访存及调度各自的耗时。

“访存带宽主导”也不表示 SIMD 永远无用。纯标量代码可能受逐元素的加载、存储及循环指令开销限制，无法充分发起访存；向量化能够帮助它接近带宽瓶颈。当 C++ 已经完成这一步，再换成 ISPC 或增加核心，就不一定有明显收益。这也解释了禁用 C++ 自动向量化后的对照结果。

## 2. 为什么 TOTAL_BYTES 是 4 × N × sizeof(float)

题目的解释采用常见的 **write-allocate + write-back** 缓存模型。缓存以整条 cache line 为单位操作，平均分摊到每个元素，可以理解为：

| 流量 | 折算 float 数量 |
| --- | ---: |
| 读 X | 1 |
| 读 Y | 1 |
| 输出写 miss 时，把包含旧 result 的 cache line 读入/取得修改所需的数据（常称 RFO） | 1 |
| 修改后的脏 cache line 最终写回 | 1 |
| 合计 | 4 |

**多出来的一份是输出的写分配读流量，不是多做了一次算术，也不是把普通写操作随意算两次。**即使程序不需要旧 result，普通写分配策略仍可能先读入整行再修改。写回通常在脏行被逐出时发生，不保证全部位于单次函数计时窗口内。

需要区分课程模型和 M3 实际硬件行为：输出若已在缓存中，就不需要重新从 DRAM 读入；完整行覆盖、硬件写流识别或非时间存储等机制，也可能避免读入即将被覆盖的旧数据。Arm 的 [Neoverse N2 写流模式说明](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/deep-dive-pmu-value-l2d-cache-wr-neoverse-n2-server)给出了避免此类分配读入的实例；这是对“4 份流量不是所有硬件上无条件成立”的说明，不能据此断言 M3 使用了相同实现。

原程序 `toBW()` 除以的是 `1024³`，所以打印的 `GB/s` 实际是 **GiB/s**。此外，它直接用 `16*N/耗时` 推算带宽，没有读取任何硬件流量计数。因此，若看到打印值超过 M3 标称 100 GB/s，不能宣布实际 DRAM 超过峰值；应先检查单位、写分配假设、缓存复用和计时窗口。CSV 同时记录 `12*N/耗时/10^9` 的逻辑有效速率，便于统一单位，但这个值也不是 DRAM 计数。

## 3. 加分优化尝试及结论

在临时源码副本中测试了逻辑 gang 宽度 4，以及 x8 下的 1、2、4、8、16、32、64、128 个任务。所有配置各运行 10 次，前两题所用的默认配置为 x8、64 tasks。没有改动原内核，也没有跳过计算或把复制、分配成本移出计时来制造收益。

本轮 task 耗时中位数最低的是 `neon_x4`，为 3.000 ms；默认值为 3.149 ms。单纯改变 task 数量，没有得到明显优于默认 64 tasks 的结果。x4 的单核和 task 耗时中位数相对默认 x8 分别约为 1.10×、1.05× 的描述性改善。但波动范围明显重叠，且相同 C++ 源码在不同配置中的基线耗时也发生变化，因此不能将这些差异视作已验证的稳定优化；本轮没有进行显著性检验。

**本轮没有达到第 3 题“显著加速”的加分目标，因此不把任何调参结果并入默认实现。**若继续优化，应先在更安静的环境中测可持续内存带宽、cache/DRAM 流量，再判断瓶颈还有多少空间。常见方向是平台支持的流式存储以减少写分配、消除真实程序中的不必要临时数组，以及与相邻计算融合以复用数据。后两者需要更大的调用上下文，不能假装是原 SAXPY 独立接口内的免费优化。

在固定带宽下，若确实能把每元素实际流量从 16 字节降到 12 字节，流量减少 25%，理想时间比才可能达到 16/12≈1.33×，远非按核心数线性增长；如果硬件本来就避免了这次读入，便没有这份收益。分块也不会让这个仅使用每个输入一次的独立算式凭空获得更多数据复用。
