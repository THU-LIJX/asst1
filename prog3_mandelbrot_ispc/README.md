# Problem 3：ISPC SIMD 与任务并行答案

本文整理 [ARM 版作业说明](../README_aarch64.md)中 3.1、3.2 及补充问题的回答，按本机 Apple M3 的情况解释。

文中的 View 1 加速比来自学习者在本次对话中提供的手工测量记录，本次整理没有重新测速，也没有原始耗时日志、重复测量或波动范围。当前源码默认仍为 2 个 task；4、8、16、32 个 task 的数值对应此前手工修改配置后的测量。构建与任务划分分别见 [Makefile](Makefile) 和 [mandelbrot.ispc](mandelbrot.ispc)。

## 3.1.1：单核 SIMD 的理想加速比与性能损失

### 理想加速比应结合硬件解释

原版课程的 Intel 机器支持 256 位 AVX 向量，一条向量算术指令可以处理 8 个 32 位 float。在课程假设标量与向量运算吞吐相近、所有通道都做有效计算且忽略其他开销的简化模型中，理想 SIMD 加速比约为 8 倍。[Intel 指令集说明](https://www.intel.com/content/www/us/en/support/articles/000005779/processors.html)

M3 的 NEON 原生向量宽度为 128 位，容纳 4 个 float。因此，在同样按原生向量宽度建立的简化模型下，可用约 4 倍作为参考值。[Arm NEON 说明](https://www.arm.com/technologies/neon)

当前 Makefile 使用 `--arch=aarch64 --target=neon-i32x8`。这里的 x8 表示一个 gang 中有 8 个逻辑程序实例，并不意味着一条 NEON 指令可以处理 8 个 float。普通逐元素 float 运算通常需要拆成两个 4 元素向量的操作，同时保持一个 8 实例 gang 的控制流语义。[ISPC 目标配置说明](https://ispc.github.io/ispc.html#selecting-the-compilation-target)

约 4 倍是基于特定假设的宽度模型，不是实际程序加速比的严格上限。标量基线、编译优化、指令吞吐和访存都影响真实比值；不能仅根据 programCount 推导严格的最大加速比。

### 为什么实际没有达到理想值

View 1 的单核 ISPC 实测加速比为 **3.46 倍**。一个重要的性能损失来源是同一 gang 内不同像素的迭代次数不同。

当前 mandel 函数在像素逃逸后执行 break。提前完成的实例会被掩码屏蔽，而整个 gang 的循环仍要执行到最后一个实例完成。例如，一组像素需要的迭代次数为：

```text
[10, 10, 10, 10, 10, 10, 10, 100]
```

后面的大部分迭代只有一个实例产生有效结果，其余通道不再贡献有效计算。不同实例的控制流不一致，会降低 SIMD 效率。[ISPC 控制流模型](https://ispc.github.io/ispc.html#control-flow-example-loops)

**集合边界附近尤其有挑战：**相邻像素可能一个很快逃逸，另一个接近最大迭代次数。同一个 gang 混入这些像素时，计算成本差异很大。相反，一组像素全部计算很久，只要迭代次数接近，仍然可以有较高的 SIMD 利用率。应关注组内计算路径的一致性，而不仅是整张图有的区域计算长、有的区域计算短。

掩码维护、循环控制及标量／向量代码生成差异也可能影响性能。3.46 倍这一结果与控制流分歧造成损失的解释相容，但仅凭加速比无法量化各因素的贡献，也不能将 3.46/4 直接当作实测通道利用率。

比较 View 1 与 View 2，可以观察不同图像的局部分歧是否对应不同加速效果。目前提供的记录只有 View 1，故不填写 View 2 的加速比或宣称哪个视图更快。

## 3.2.1：两个 task 的加速效果

| 实现 | 相对串行版本的加速比 |
| --- | ---: |
| 单核 ISPC | 3.46 倍 |
| ISPC，2 个 task | 6.75 倍 |

使用同一串行基准时，任务版本相对于单核 ISPC 的提升为：

```text
S_task / S_ISPC = T_ISPC / T_task = 6.75 / 3.46 ≈ 1.95
```

**回答：**每个 task 内部仍然使用 SIMD，不同 task 又可以在不同核心上并行执行。两个 task 将图像划分为上下半图，工作量接近，所以在 SIMD 加速基础上又获得约 **1.95 倍**的提升，接近理想的两倍。总加速比为 6.75 倍，而不是总共两倍。

需要区分任务与核心：launch[2] 提交两份工作，并不保证两个 task 固定绑定到指定核心。它们由运行时和操作系统调度，也可能随时间迁移。这里的接近两倍提升支持多核并行有效的解释，但没有核心追踪数据来确认具体使用了哪些核心。

## 3.2.2：task 数量的选择与原因

### 测量记录

| task 数量 | 相对串行版本的加速比 |
| ---: | ---: |
| 2 | 6.75 倍 |
| 4 | 8.26 倍 |
| 8 | 12.66 倍 |
| 16 | 16.76 倍 |
| 32 | **17.18 倍** |

**选择方法：**逐步增加 task 数量，比较性能，直到增加任务带来的收益明显缩小。在已经测试的配置中，32 个 task 的加速比最高，为 17.18 倍，可以作为本次测量下的选择。

不过，32 相比 16 的加速比仅增加约 **2.51%**，16 个 task 已经接近平台期。没有重复测量和波动范围时，不能判断这点差异是否稳定，也不能宣称 32 是所有输入和运行条件下的全局最优。

### 为什么更多 task 可以提高性能

合理解释是，更细的任务划分同时改善了核心利用和任务间负载分配：

- task 太少时，没有足够的工作份数供多个核心同时执行。
- 连续行块的像素迭代量不同。某个较大 task 计算时间很长时，其他工作线程可能已结束自己的工作而空闲。
- task 数量多于执行线程数时，完成当前工作的线程可以继续处理队列中的任务，从而减轻粗分块造成的等待。这对不同速度的性能／能效核心也有帮助。
- task 过多则可能增加提交、调度和同步开销，需要在任务粒度与负载均衡之间取舍。[ISPC 任务划分建议](https://ispc.github.io/ispc.html#task-parallelism-launch-and-sync-statements)

**task 数量不等于核心数量。**本机 M3 有 4 个性能核心和 4 个能效核心，不会因提交 16 或 32 个任务而增加核心。超过 8 个 task 后继续改善，可以由更细的任务划分解释，不能归因于 M3 的超线程。增加 task 也没有改变 NEON 的原生 SIMD 宽度。

这些原因与数据相容，但没有逐任务耗时或核心分配记录，尚不能逐一确认其贡献。原版 Intel 环境的超过 32 倍目标不直接用于评价本机；ARM 版要求在实际硬件上获得显著改善。

### 修改配置时的要求

只在 mandelbrot_ispc_withtasks 中修改任务数时，要同步调整 `rowsPerTask = height / task 数量` 与 `launch[task 数量]`，保持行块大小和任务数一致。当前图像高度为 800，能被本次测试的 2、4、8、16、32 整除，各任务应恰好覆盖整张图而不重叠。

性能记录只有在串行参考结果校验通过时才有效。若以后使用不能整除高度的 task 数量，还需另行处理余数行；不能直接沿用当前整数除法划分。

## 3.2.3：thread 与 ISPC task 的区别

“thread 的开销比 task 大”通常适用于每份工作都新建一个系统线程的比较，更核心的区别是两个抽象管理的对象不同。

| 方面 | std::thread | ISPC task |
| --- | --- | --- |
| 表达的对象 | 一条独立执行线程 | 一份待执行的工作 |
| 创建方式 | 创建系统线程及执行上下文 | 向任务运行时提交工作 |
| 执行资源 | 拥有线程栈与执行状态 | 通常复用工作线程，使用工作线程的栈执行 |
| 工作分配 | 通常由程序显式安排，也可自行实现任务池 | 由任务运行时将任务分配给工作线程 |
| 等待方式 | join 等待指定线程结束 | sync 等待当前函数启动的任务完成 |

ISPC 的 launch 是异步提交，不保证任务执行顺序，也不保证提交后立即执行。sync 等待当前函数启动的任务，而不是系统中所有任务；启动了任务的函数返回前会执行隐式 sync。[ISPC 任务语义](https://ispc.github.io/ispc.html#tasking-model)

### 10000 个 task 与 10000 个 thread

在通常使用线程池的任务运行时中，启动 10000 个 task 是提交 10000 份工作。队列保存任务描述和参数，由运行时管理的一组工作线程逐批执行，不必给每个待执行任务都创建独立系统线程和栈。

创建 10000 个 std::thread 则需要大量线程执行上下文和栈资源。若大量线程同时可运行，还会产生很大的调度竞争、上下文切换及缓存扰动，甚至可能因为资源限制而创建失败。

**因此，task 将工作数量与执行线程数量分开了。**它仍然通过线程执行，具体开销和并发规模取决于任务运行时。自己使用 std::thread 实现并复用线程池，也能获得类似效果；不能说任何线程方案都比 task 方案慢。

本仓库在 macOS 上使用 GCD：任务提交到全局并发队列，由系统管理工作线程，任务组负责等待完成，见 [tasksys.cpp](../common/tasksys.cpp)。GCD 提供自动线程池管理，避免程序为每份工作自行管理一个线程。[Apple GCD 说明](https://developer.apple.com/library/archive/documentation/General/Conceptual/ConcurrencyProgrammingGuide/ConcurrencyandApplicationDesign/ConcurrencyandApplicationDesign.html)

任务也并非没有开销。10000 个过小的计算任务仍可能让排队和调度成本超过计算收益，应选择足够大的任务粒度。

## 补充问题：为什么同时需要 foreach 和 launch

题目问：既然 foreach 已经表达了独立迭代，为什么编译器不直接把这些迭代分配到所有核心，并同时生成 SIMD 代码？

**回答：可以设计这样的编译器或并行框架。ISPC 将两者分开，是为了让程序控制跨核心工作划分，并方便与已有并行系统组合。**

| 机制 | 负责的层次 |
| --- | --- |
| foreach | 将迭代映射到一个 gang 的实例，由编译器生成 SIMD 指令 |
| launch | 提交多份独立任务，由运行时安排跨线程／跨核心执行 |

每个 task 内部仍然可以使用 foreach，所以两种机制可以组合使用。保留两个层次有以下理由：

1. **任务粒度需要选择。**一个像素一个 task 容易产生大量调度开销，整张图一个 task 又无法利用多核。Mandelbrot 的计算成本还随位置变化，本次任务数扫描表明不同划分的性能差异明显。编译器可以使用启发式自动划分，但很难保证所有输入都得到最佳粒度。
2. **调用者可能已经在使用多核。**例如，C++ 线程池并行处理多张图片，每个工作线程再调用 ISPC 处理一张图。如果每次 foreach 都自动启动多核任务，可能形成嵌套并行并增加调度和资源竞争。默认保持单核 SIMD，调用者更容易控制并行资源。
3. **小任务未必适合跨核心。**跨核心执行需要任务提交与同步；小规模循环可能很快结束，启动和等待成本反而超过收益。显式 launch 让程序选择哪些工作值得跨核心执行。

因此，编译器负责如何向量化，程序与任务运行时负责如何利用多核。对于本作业，launch 将图片分成多个任务，各任务内的 foreach 再执行 SIMD，两层并行共同产生加速。[ISPC 任务与 SIMD 的组合方式](https://ispc.github.io/ispc.html#task-parallelism-launch-and-sync-statements)
